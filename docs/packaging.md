# Packaging: the .exe (PyInstaller, a folder build)

**Result.** A folder, not a single file:

```
PullsTracker\
  PullsTracker.exe      the program (no console window)
  _internal\            Python, libraries and the interface (pulls_tracker_ui); read only, do not edit
  data\                 made at the first start: settings, pulls, downloaded art, log, browser storage
  README.txt            short instructions for whoever uses the folder (from dist_README.txt)
```

The whole folder is the program. Everything the program writes goes in `data\` beside the .exe (`pt/paths.py`: `data_dir()` is the folder of the .exe plus `data`; the interface is read from PyInstaller's `_internal` folder). Moving, copying or backing up the folder moves the program with its settings and assets. A one-file build is not used: it unpacks itself into a temporary folder at every start (slow, antivirus programs distrust it) and has no stable place for the data.

**Build on Windows** (Python 3.10 to 3.13, 64 bit):
1. Open a command prompt in the project folder.
2. Run `build_exe.bat`. It makes the virtual environment `.venv-build` in the project folder (the installed Python is not changed), installs `requirements.txt` and `requirements-build.txt` in it (pywebview with pythonnet, PyInstaller), runs `PyInstaller --noconfirm --clean pulls_tracker.spec`, copies `dist_README.txt` into the folder and runs the self check (the script ends with an error code when the build or the self check fails). It stops with exit code 3 before it builds when `dist\PullsTracker\data\pulls.sqlite` exists, because the build replaces the whole `dist\PullsTracker` folder: move the `data` folder out first.
3. Copy `dist\PullsTracker` (the whole folder) to where you keep the program, for example `D:\PullsTracker`.

To see errors while testing, build with a console window: `set PT_CONSOLE=1` before `build_exe.bat`. 

**Your own icon (`.pyw`/`.py` and `.exe`).** One file, `pulls_tracker.ico`, in the project folder (next to `pulls_tracker.spec`), does both:
1. Make the file from your picture: `python -m pip install pillow`, then `python make_icon.py my_design.png`. It writes `pulls_tracker.ico` with the sizes Windows uses (16 to 256 pixels). Use a square PNG of 512 x 512 pixels or more, with simple, thick shapes.
2. **The .exe:** run `build_exe.bat` again. The spec puts the icon on `PullsTracker.exe` (what Explorer, the desktop and the Start menu show) and also copies it into `_internal`, where the program reads it to give the **running window and its taskbar button** the same icon (`pt/appicon.py`, `set_window_icon` in `pt/window.py`). The line `icon of the window:` of `PullsTracker.exe --selfcheck` shows the file it found. If Explorer still shows the old icon after a rebuild, that is Windows' icon cache: copy the folder to a new name or restart Explorer.
3. **The .pyw (or .py):** the running window and its taskbar button get the icon from `pulls_tracker.ico` next to the script, and the taskbar no longer groups it under Python (`SetCurrentProcessExplicitAppUserModelID`, only when run from source). The **file** `pulls_tracker.pyw` itself cannot carry an icon (Windows shows the icon of Python files for every script). To have your icon on something to double click: right-click the `.pyw`, Send to, Desktop (create shortcut); then Properties, Shortcut, Change Icon, Browse, pick `pulls_tracker.ico`.
Without `pulls_tracker.ico` nothing changes (the default icons).

**What the spec does** (`pulls_tracker.spec`): the interface folder goes in as data; `banner_tracker_test` (the fetcher, imported by name) and the program's own modules are hidden imports; pywebview's scripts and, on Windows, its WebView2 files (`WebView2Loader.dll`, `Microsoft.Web.WebView2.*.dll`) and the pythonnet files are collected; the other pywebview backends (Qt, GTK, Tk) are excluded so they are not pulled in.

**Where to put it.** In a folder you can write to (`D:\PullsTracker`, `C:\Users\<you>\PullsTracker`). In `C:\Program Files` the program cannot create `data\` there; it then uses `%LOCALAPPDATA%\PullsTracker\data` and says so in the log and in the self check. The environment variable `PULLS_TRACKER_DATA` sets the data folder in any case. A folder inside OneDrive, Dropbox, Google Drive, iCloud, MEGA or pCloud (`paths.cloud_folder`) works but is not advised: the pull database is a SQLite file in WAL mode, and a sync program that locks or rewrites it while the program runs can damage it. The log, the self check and Settings > Privacy and storage (which also shows the data folder) say so. Desktop and Documents are inside OneDrive on many Windows computers.

**Sharing the .exe with other people (checks made at the start, `pulls_tracker.py`, `pt/preflight.py`, `pt/single.py`).**
- *One copy per data folder.* A named mutex on Windows (`Local\PullsTracker-<hash of the data folder>`), a lock file elsewhere. A second start shows "already running" and ends. Another folder is another copy with its own data. If the guard itself fails the program starts anyway.
- *WebView2 check.* Without the runtime pywebview falls back to an old engine and the window stays blank, with no console to say why. The program reads the runtime's version from the registry first; when it is missing a box offers the download page (Yes opens it and ends, No starts anyway).
- *A start that fails is reported.* Any error before the window is open (a module missing from the build, a data folder that cannot be created) is written to the log and shown in a message box with the error and the log path. The windowed program otherwise ends without a trace.
- *Database format.* `data\pulls.sqlite` records a format number (`meta.schema`, `pt/store.py`). When a new .exe replaces an old one the database stays, so: a database of an older format is migrated by the steps in `store.MIGRATIONS` after a copy named `pulls.sqlite.before-format-N` is made (a failing step is rolled back and the program reports it); a database of a newer format is not opened (message, nothing changed, the file is not treated as damaged). `MIGRATIONS` is empty because the format has not changed yet; a version that changes a table adds its step and raises `SCHEMA_VERSION`.
- *Updating.* Replace `PullsTracker.exe` and `_internal\`, keep `data\` (`dist_README.txt` says this to the user). `settings.json` is read with defaults for keys it lacks, so a newer version's settings are added without a migration.
- *Nothing is written outside the data folder* (tested; see below), except: the file you choose in the Save dialog of an export (written through a temporary file in the same folder, removed if the export fails), the backup folder when Settings names one outside the data folder (only `pulls-<date>-<time>.sqlite` files are written or removed there), the Windows mutex (not a file), a short-lived copy of the game's cache in the system temp folder when the game has the file locked (deleted at once), the optional HoYoLAB cookie in the system keyring, and, with the old IE engine only (no WebView2), pywebview's own registry entries.
- *Not signed.* The .exe has no publisher signature, so Windows SmartScreen shows "Windows protected your PC" on the first start (More info, then Run anyway) and an antivirus program may inspect or flag it. The build avoids the things that raise this (no UPX, a folder build instead of a one-file build). A signing certificate is the only complete remedy and costs money; it is not part of this project.

**The computer that runs it** needs Windows 10 or 11 and the Microsoft Edge WebView2 runtime (already on Windows 11 and on updated Windows 10; otherwise the Evergreen runtime from Microsoft). The Python installation is not needed.

**If the .exe does not start or the window is blank:** run `PullsTracker.exe --selfcheck`. It checks the data folder, the interface files, the modules that are loaded by name (`banner_tracker_test`, pywebview, pythonnet, the WinForms and WebView2 parts of pywebview) and the WebView2 runtime, shows the result in a message box (there is no console) and writes `data\selfcheck.txt`. Then read `data\pulls_tracker.log`. `--debug` enables F12 in the window. Setting `PULLS_TRACKER_NO_PATCH=1` turns off the pywebview/WebView2 handler change (`pt/winpatch.py`), to find out whether it matters.

**Your loading banner** goes in `data\assets\loading\banner.png` (`.webp`, `.jpg`, `.jpeg` also work); it is read before the banner inside `_internal`.

**What was tested.** In the sandbox this was written in (Linux, no Windows), the same spec built a folder build with PyInstaller 6.22 and `--selfcheck` passed (all modules, including the stage 2 and 3 ones, SQLite in WAL mode in the data folder). A second build with the Qt backend (a stand-in for WinForms; 561 MB because it carries Qt) was run: from a folder with spaces and an accent in its name (`Pasta Única/Pulls Tracker`), started from another working folder with an empty home folder; it opened the main screen from `_internal` in backend mode and wrote only into `data\` beside the program (database, settings, log, assets, browser storage, lock file; nothing in the home or working folder; the only other new item was a `locales` folder that Qt itself makes inside its own bundle); a second copy started while the first ran logged "Another copy is running" and ended with exit code 0; as an unprivileged user from a folder that user cannot write, the data went to the fallback folder (`$XDG_DATA_HOME/PullsTracker/data` there, `%LOCALAPPDATA%\PullsTracker\data` on Windows), the program folder stayed unchanged, and the log said why. The unit tests (`tests/test_deploy.py`) cover the guard, the WebView2 decision logic with a stand-in for the box and the registry, the sync-folder names, the database format (new, newer, older with a step, failing step, missing step), the start failure and the rule that a child process started with new data, home and working folders writes only into the data folder.

**Not tested here, and the reason:** everything that exists only on Windows: the mutex call (`CreateMutexW`), the message boxes (`MessageBoxW`), the registry read of the WebView2 version, and the WinForms and WebView2 behaviour of pywebview, because there is no Windows in the sandbox; and the live game servers (see "Account sync"). These pieces were written to fail open (the program starts when a check itself fails) and to be tested with stand-ins, but they have not run on Windows. On the first Windows build: run `--selfcheck`, start two copies, start from a folder with a space and an accent, and start once from `C:\Program Files`. If the build fails or `--selfcheck` reports a FAIL, `data\selfcheck.txt` and the log are what is needed.
