# Account sync (v34)

"Sync now" reads the pull history from the game's own history service, using the temporary link the game saves on this computer when you open its pull history page. **Not run against the live service:** the sandbox this was written in cannot reach the game's servers and has no game installed. The whole sync was run against a made-up service that answers in the format described in the analysis notes (`tests/test_sync.py`, 61 tests), and in the real application window against the same made-up service. Items marked **[U]** below are taken from those notes and not confirmed on a live account.

The four steps of the Sync screen:
1. **Find the game cache.** The folder chosen in Settings (searched up to 4 levels down for a `webCaches` folder), then the folders named by the game's own log files in `%USERPROFILE%\AppData\LocalLow`: Genshin `miHoYo\Genshin Impact\output_log.txt`, `miHoYo\原神\output_log.txt`, `Cognosphere\Genshin Impact\output_log.txt`; Star Rail `Cognosphere\Star Rail\Player.log`, `miHoYo\Star Rail\Player.log`; Zenless Zone Zero `miHoYo\ZenlessZoneZero\Player.log`, `Cognosphere\ZenlessZoneZero\Player.log` **[U]**. Every `data_2` file below the `webCaches` folders is a candidate, newest first. A file the game has locked is read from a copy.
2. **Find a valid link.** Addresses with an `authkey` are taken from the newest cache file that has any, the one nearest the end of the file first (at most 40). The `timestamp` in an address is not used: it is not the time the game made the key (on Zenless it was 23 days old for a key made hours before). Each address is tested with a one-item request (8 seconds; a lost request or an HTTP 5xx/429 answer is tried once more, an answer about the key or HTTP 404 is final). An answer that mentions the key counts as an expired key whatever its code or spelling (Genshin says "authkey timeout", Zenless "auth key time out"). The first address the service accepts is used. The Sync screen shows the age of the cache file. Only addresses on the game company's hosts (`hoyoverse.com`, `mihoyo.com`, `hoyolab.com`) and of the right game (`game_biz`) are considered. The key is sent back exactly as it is in the file and is never written to the log (a test checks this). If the first address gets no answer at all the others are not tried (offline).
3. **Fetch the history.** Each banner type is read page by page, newest first: 20 items a page, the next page asks for items older than the last ID of this one (`end_id`), and the list ends with an empty page. About 0.6 seconds between requests. "Too frequently": wait 15 seconds and ask again, up to 5 times, then stop with "Stopped by the server". A network error is tried 2 more times. Zenless Zone Zero repeats the banner type as `real_gacha_type`. Genshin Chronicled Wish (type 500) is asked for as well and stored; if the service refuses it, that is ignored **[U]**. Names are requested in English (the banner data is English); if the service refuses that, the language of the saved link is used and the result says the 50/50 results may be wrong.
   - A banner type that was read to its end before is read again only until the first page that holds a pull already stored. The first sync, a banner type that was never completed, and a banner type of a cancelled sync are read to the end. The "complete" mark is set only when the service gave the empty page.
   - Each banner type is merged into the database when it is complete, so a cancel, a rate limit or an error keeps the banner types already finished.
4. **Merge into the local database.** The account's last sync time and UTC offset (the service's `region_time_zone` when it gives one, else the offset of the UID's region) are saved. Before the first write of a sync, a copy of the database goes to the backup folder (Settings > Storage, "automatic backup" on), unless the database is empty or the newest backup is less than 6 hours old; the newest 10 are kept.

- **Which account.** The UID comes from the pulls themselves. A UID already stored for the game is accepted and becomes the account the screens show. A UID that is not stored while another is stops the sync before anything is written ("This data belongs to another account"); "Add as new account" runs it again accepting the new UID. The first account of a game is added without asking.
- **First-run screen.** `firstRun()` reports, per game, whether a game folder was found and how old the newest cache file is (a link older than about a day is probably expired).
- **One sync at a time**, in its own thread; the screen gets events (`step`, `fetch`, `wait`, `done`, `error`) through `evaluate_js`. Cancel stops it between requests; nothing is sent to the page after a cancel. Closing the window also stops it. Pulls are written one banner type at a time in a transaction.
- **Sync at start** (load task 7): only for a game that is tracked, has an account whose banner types were all read to the end, and whose cache file changed less than 24 hours ago. It stops after the first page it already has. The first sync is always yours. The result of each game is in the log.
- **Errors the screen shows:** `cache_missing`, `cache_unreadable`, `link_expired`, `rate_limited`, `network`, `server_error` (with the service's message), `uid_mismatch`, `internal` (the traceback is in the log). Pulls already merged stay stored in every case.
- **Notes on the result card:** banner types the program has no screen for (stored), names not in English, items skipped for lack of an ID, time or rarity, a backup that could not be written.
- **Data sources > Test** asks the calendar server (or the address saved in Settings) for the current banners. The address saved in Settings is now also used by the load task that checks the active banners.
- **HoYoLAB cookie** (Settings > Data sources). With the optional `keyring` package (Windows Credential Manager) the value is stored in pieces of 600 characters (the Credential Manager limit is about 1280) and is never written to the settings file or the log. Without the package the screen says it cannot store it. **Nothing reads the cookie yet:** there is no HoYoLAB source in this version.

**[U] not confirmed on a live account:** the response fields and `retcode` values (the program matches the message text first, as the reference program does, and also -100 and -101 for the key and -110 for "too frequently"); the log file names and folders above; that the `data_2` file holds the address in the form the tests use; that the `lang` override is honoured; the codes 500 (Genshin), and the Star Rail and Zenless Zone Zero banner types; the time zone offsets by UID prefix; locked-file behavior on Windows. If a sync fails in a way the screen does not explain, `data/pulls_tracker.log` has the step, the error code and the service's message (never the key).
