# Pulls, pity and statistics (v33)

The data side of the screens. **What works in this version:** storing pulls, pity and guarantee, history, statistics, settings, accounts, UIGF v4.0 and CSV import and export. Reading pulls from the game is the next section ("Account sync", v34); a UIGF v4.0 file from another tracker can also be imported.

- **Database** (`data/pulls.sqlite`, SQLite, write-ahead log). One row per pull, keyed by game, UID and the game's pull ID, so the same ID in another game or account is another row. IDs are kept as text and ordered as integers (never as floating point numbers). New pulls are added with insert-or-ignore: a stored pull is never changed or duplicated by a sync or an import; what the columns do not hold stays in a raw JSON column. A damaged file is renamed (`pulls.sqlite.damaged-<time>`) and a new database is started, and the log says so. The Beginner banner and banner types the program does not know are stored too, but have no screen.
- **Pity, guarantee and results are never stored.** They are computed from the stored rows each time (`pt/engine.py`) and cached until a row, a banner or a setting changes, so changing the Star Rail loss pool changes every result at once.
  - Pity is the number of pulls since the last 5-star of the same banner type, oldest pull first. Genshin Wish 1 and Wish 2 are one counter. The first 5-star of a banner type has a pity that is only a lower bound (`≥`): the history may start in the middle of a count (the servers keep a limited history, or the account was played before the first import). A banner type with pulls and no 5-star shows its current pity as "at least".
  - A 5-star on a 50/50 or 75/25 banner is classified as featured or not. In this order: the featured 5-stars of the banners whose window (start to end, 2 minutes of slack) contains the pull, from the **banner history**; otherwise, for Genshin and Zenless Zone Zero character banners, a list of standard 5-stars (`STANDARD_5` in `pt/games.py`, which you can correct in `data/rules.json`: `{"standard5": {"genshin": ["Diluc", ...], "zzz": [...]}}`); for the Star Rail character banner, your loss pool (Settings); for the Star Rail Light Cone banner, the permanent 5-star Light Cones (`"hsr_lightcone"` in the same list and the same `data/rules.json`; a Light Cone the game adds to the permanent pool must be added there). Where none applies (Genshin and Zenless weapon banners with no banner data) the result stays empty and the guarantee is "unknown". Names are compared without regard to case, extra spaces and curly or straight apostrophes.
  - A 5-star after a lost 50/50 is "WON guaranteed" (not counted as a flip). The first stored 5-star's guarantee is unknown: a win there is shown as an assumed 50/50 with "(?)", a loss is not assumed.
  - Luck grade: the average pity of the 5-stars against the thresholds of Settings. Spent: pulls x 160 (the Beginner banner is not counted).
  - The Capturing Radiance counter is an estimate (consecutive lost 50/50s); the game's own counter is not in the data the game gives. The Epitomized Path and the selected Bangboo are not shown (not in the pull history).
- **Banner history** (`banner_archive` table). Each start, the banners of the shipped snapshot and of `data/js/banners.js` are copied into the database; banners that a later file no longer lists stay. Past Banners reads them. It only knows banners this program has seen, so it starts with the current ones and grows.
- **Times.** The game gives pull times in the server's time zone. They are converted to UTC with the UTC offset of the region of the UID (`region_of` in `pt/games.py`: Genshin and Star Rail 6 America -5, 7 Europe +1, 8 Asia +8, 9 TW/HK/MO +8; Zenless Zone Zero 10 America -5, 13 Asia +8, 15 Europe +1, 17 TW/HK/MO +8; no daylight saving time is applied, which is what the game servers use [not checked against a live account]). Screens show times in Local, Server or UTC (Settings); the date filter of the History screen uses the days of that same mode.
- **Accounts.** An account is created by the first import or the first sync for a game. The screens show the one a sync or an import touched last. An import file for another UID than the stored account(s) of that game is blocked (the screen says so).
- **Import.** UIGF v4.0 JSON (`hk4e`, `hkrpg`, `nap`; several accounts in one file are fine) and the CSV this program exports. A preview counts new pulls, pulls already stored and conflicts (same ID with another time, rarity or banner); you choose "Keep stored" or "Use file" for conflicts. Nothing is written before "Import". Files up to 100 MB. Not read: UIGF versions other than v4.x, other CSV layouts. The page cannot name a file to read: `importPreview` reads only the path chosen in the dialog of `pickImportFile`, and answers the same refusal for any other path, existing or not.
- **Export.** UIGF v4.0 JSON (every stored pull of the account, the Beginner banner included; `uigf_gacha_type` 400 is written as 301) and CSV, for all time or the last 12 months, 90 or 30 days; the History screen exports the rows of its filter as CSV. The application asks where to save; a cancelled dialog writes nothing. **[U] The UIGF layout follows the v4.0 page of the standard; the official validator was not run on the files, and fields added in v4.2 are not written.**
- **Settings** are validated before they are saved (ranges, order of the thresholds, loss pool size) and written to `data/settings.json` through a temporary file, so a crash cannot leave half a file. A `settings.json` that cannot be parsed is kept as `settings.json.bad` (the defaults are used; the next save does not overwrite the copy), and a backup folder that is not an absolute path is reset to the default one.
- **Image cache** (Settings > Storage) is the size of `data/assets/art`; "Clear" deletes those files, and the next start finds them missing and downloads them again. It refuses (and says so) when `data/assets/art` is a link that leads outside `data/assets`, so a link can never make it delete another folder; files that stay because another program holds them are counted in the message.
- **Backups** (Settings > Storage, v35). A backup is a consistent copy of `pulls.sqlite` named `pulls-<date>-<time>.sqlite` in the backup folder (`data/backups` unless Settings names another folder); the newest 10 are kept; only files named exactly like the ones the program writes are counted and removed, so anything else in that folder is never touched. With "Back up automatically" on, one is written before the first write of a sync (skipped when the newest is under 6 hours old), before an account is removed, and before an import that replaces pulls ("Use file" with conflicts); the last two ignore the 6 hours. "Back up now" writes one whenever you press it. A backup that cannot be written is logged and does not stop a sync or a removal. Settings shows how many files the folder holds, their size and the time of the newest. **To restore:** close the program, copy the backup file over `data/pulls.sqlite` (delete `pulls.sqlite-wal` and `pulls.sqlite-shm` next to it first), start the program. There is no restore button.
- **Several accounts of one game** (v35). The screens show one account per game, the one marked "Shown". The Dashboard header has a list when the game has more than one account; Settings > Accounts has a "Show" button on the others. The choice is kept in the database (the time the account was last shown).
- **5-star timeline** (History, v35). Above the table, a chart of the 5-stars of the current filter (all pages, oldest to newest): left to right is time, height is the pity of each one, the colour follows the pity colors of Settings, a hollow circle is a lower bound, a ring is a lost 50/50 or 75/25. It is hidden when the filter has no 5-star.
- **Errors.** A method that fails is written to the log with its traceback and answers its fallback plus `error` and `failed: true`. The page raises that and shows the text, so a screen never waits for a call that was never answered and never shows a failure as an empty history (contract in `pulls_tracker_ui/README.md`). An answer that only has an `error` text, such as a refused import, is the screen's own message.
- **Tests:** `python -m unittest discover -s tests` runs 310 tests (`tests/` has no `__init__.py`, so the start folder is named; `test_ui_pages.py` runs the pages in Chromium through Playwright and is skipped when Playwright is not installed). `test_backend.py` (normalizing, UIGF and CSV round trips, the store, the guarantee state machine, every screen's answer, import conflicts, export, settings, the file-safety checks), `test_stage3.py` (accounts, backups, the timeline), `test_sync.py` (the sync against a made-up service, the keyring wrapper), `test_banners.py` (the fetcher), `test_window.py` and `test_winsize.py` (the window layer with fakes, so no Windows call runs), `test_loader.py`, `test_deploy.py` (paths, build files, self check), `test_audit_fixes.py` (the fixes of the second audit, see AUDIT_CHANGES.md; each of its tests fails on the code as it was before the fix). They use made-up pulls; the real window was also run on a seeded database in the sandbox, and the page in headless Chromium with a stub bridge. A test never touches a real data folder (each test module clears `PULLS_TRACKER_DATA` and each test sets its own). **No real account was used: the sandbox has none.**
