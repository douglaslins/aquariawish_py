# Start-up: loading panel, load tasks, main screen (v27)

`pt/window.py` opens one frameless pywebview window for the whole run.
1. It starts as the **loading panel**: 803 x 230 pixels, dragged by clicking anywhere on it. The left 230 x 230 area has the donut and, under it, a small label with the running task; the right 573 x 230 area shows your banner (`pulls_tracker_ui/assets/loading/banner.png`, also read as `.webp`, `.jpg`, `.jpeg`; without a file it is a plain dark area). Preview in a browser: `pulls_tracker_ui/loading.html?demo=1`.
2. The load tasks of `pt/loader.py` run in order and move the donut. The task functions are in `pt/tasks.py`, the banner and asset engine in `pt/banners.py`; the network work is done by `banner_tracker_test.py` (the fetcher, unchanged), which the engine imports.
   - **1 Check the active banners:** reads the calendar of each game (`api.ennead.cc`). After a network error the other games are not tried (offline).
   - **2 Look for stored data:** reads `data/js/banners.js`.
   - **3 Check that it is up to date:** per game, compares the banners that are active now (name, start, end and featured items) with the stored ones, and checks that every stored art and icon file exists. Images that could not be downloaded last time are tried again at a start more than 6 hours later. A game whose calendar could not be read counts as up to date: what is stored stays in use.
   - **4 Branch:** a game that is up to date skips its download task, so the donut moves on over the tasks that remain; when all three are up to date, nothing is downloaded.
   - **5 to 7 Download the Genshin Impact, Honkai: Star Rail and Zenless Zone Zero assets:** for the characters and weapons of that game's active banners: art, icons and descriptions, saved under `data/assets/art/<game>/`; `data/js/banners.js` is rewritten after each game. The donut moves with each item (`ctx.progress`).
   - **7 Account syncs:** runs `pt/sync.py` `auto_sync` for each game that qualifies (see "Account sync" below: an account whose full history is stored and a saved link younger than 24 hours). It never starts a first sync, stops after 60 seconds in all, and a failure is only written to the log.
   - A label stays visible at least 0.3 s. A task that fails is written to the log and loading goes on.
3. The last task, "open", sets the donut to 100%, hides the window, sets it to 1191 x 930 around the same centre (smaller only when the screen cannot hold it), loads the main page (`index.html#backend=1`, see below) and shows the window when the page says its first screen is ready (`WindowApi.uiReady`; after 20 s it is shown anyway).
- **Offline or the services down:** the tasks that need the network fail quickly, the panel still runs, and the main screen uses `data/js/banners.js` if it exists, otherwise the snapshot shipped in `pulls_tracker_ui/js/banners.js`. The Dashboard and Banners screens show the age of the banner data.
- **Where the data goes:** the interface folder is read only in the `.exe`, so everything the tasks write goes to `data/`, which has the same layout as the interface folder for these files (`data/js/banners.js`, `data/assets/art/...`). When `data/js/banners.js` exists the main page is opened with `#backend=1&data=<data folder>` and reads banners and art from there (`js/banners-base.js`).
- **Not run against the live services:** the sandbox this was written in cannot reach them. The tasks were run with canned answers in place of the network (through the real fetcher code, `tests/test_banners.py`), including inside the real window.
- The main page draws its own minimize and close buttons, and the whole top bar moves the window when you drag an empty part of it (`easy_drag=False`: only drag regions move it; the region is a layer under the bar, so the tabs and buttons stay clickable). Minimize and close reach Python through `WindowApi`.
- **Window behavior:** the window is never "always on top" unless you turn on Settings > Display > "Keep the window above other windows" (off by default, applies at once, saved in `data/window.json`, `WindowApi.windowSetOnTop`). Each window (the panel, then the main window) is brought in front once when it appears, without staying there. Before v30 the panel was created on top and switched off from a background thread; both windows now start as normal windows and the property is only changed on the window's own thread.
- **Resize handles:** a frameless window has no edges the system can grab (pywebview adds none, checked in its source), so the page draws eight handles (4 edges 6 px wide, 4 corners 8 px, also inside the dialogs; `js/window.js`, `css/app.css`). On Windows one call when the button goes down (`windowStartResize`) starts a thread (`pt/winsize.py`) that follows the cursor with `GetCursorPos`, `GetAsyncKeyState` and `SetWindowPos` until the button is released, so no message crosses the WebView2 bridge while the mouse moves. Elsewhere the page does the same job with `windowGetRect` / `windowSetRect`, one call in flight and at most one per frame. The smallest size is 960 x 720 CSS pixels (`winsize.MIN_SIZE`, the interface was checked at that size: no horizontal overflow on any screen); the Windows screen scale is taken into account. Not run on Windows in the sandbox where this was written: the Win32 loop is tested with a fake cursor (`tests/test_winsize.py`) and the page-driven route inside the real window (Qt).
- **Responsiveness audit (v30):** after the main window opened, clicks seemed to freeze it on Windows. In the sandbox the page was profiled in Chromium (headless and inside the real pywebview window, with real mouse events): no timers other than two 30-second ones, no observers, no scroll or mouse-move listeners, 1100 to 1400 page elements, no work while idle, every click finished in under 80 ms with 60 frames per second, no request loops. The page code does not loop, so the cause of the freeze on Windows is not proven. What was found and changed in the window layer: (1) pywebview 6 runs a Python function on the window thread for every file the page loads and every response (it builds a dictionary of all the headers and raises events nobody here listens to); `pt/winpatch.py` removes that. (2) `WindowApi` exposed a `threading.Event` to the page, which made pywebview publish its methods too; it is private now. (3) The window is no longer created on top and switched off from another thread. If it still freezes, run `python pulls_tracker.py --perf --debug`, click around until it freezes, close the program and send `data/pulls_tracker.log`: the lines `perf {...}` say whether the page was blocked (`stalls`, `longTasks`), drawing was slow (`afterClick`, `frames`), or a call to Python was slow (`slowCalls`); `--debug` also allows F12 and the Performance tab of the developer tools.
- **The address has no `?`:** the main page is opened as `index.html#backend=1&data=...`, with the parameters in the fragment. In the Windows WebView2 host a `?` in a `file://` address becomes part of the file name and the window shows "File not found" (this happened in v27 and v28). `js/params.js` in the interface reads the fragment and the query string into one set of parameters.
- Closing the window while it loads (Alt+F4) stops the start. If the main page cannot open, the program ends and the reason is in the log.
- Browser storage (WebView2 profile, cache) is in `data/webview` next to the program; the log is `data/pulls_tracker.log`.
- The Python side answers the data methods (see "Pulls, pity and statistics"); the sync methods are in "Account sync". Methods it does not have are answered by the page: the read ones as an account with no data, the others as "not available yet". `sources()` (the banner data table) is still answered by the page.
